# 01 角色与职责

> 原则：本项目按**角色（Role）**而非人头配置。个人开发时一人可兼多岗，但「作者」与「评审人」必须分离；AI 编程代理是执行者，永远不是评审人。

## 1. 角色总表

| # | 角色 | 核心使命 | 关键职责（做什么） | 主要交付物 | 评审权 |
|---|---|---|---|---|---|
| R0 | **产品负责人 / 求职领域专家**（本人） | 保证系统服务真实求职目标 | 定筛选条件与薪资/通勤口径、确认候选区、审核招呼语与简历、确认聊天事件、审批策略建议、UAT | 需求清单、Filter Set 决策、候选确认记录、UAT 结论 | 需求/候选/文案/策略终审 |
| R1 | **架构师 / Tech Lead**（本人兼任） | 守住边界与契约 | 领域划分、ADR、契约冻结、任务拆解、评审门把关、技术选型争议裁决 | ADR、契约冻结记录、架构评审结论、阶段 Go/No-Go | 架构/契约/红线初审 + 终审组织 |
| R2 | **后端工程师** | 领域逻辑与数据流 | FastAPI 域模块、Worker、Alembic 迁移、幂等/事件/Outbox、REST/WS Gateway | 域服务代码、迁移、API、单测/集成测试 | 无（被 R1/R8 评审） |
| R3 | **AI / 算法工程师** | 让 AI 输出可控可溯 | Prompt Registry、Provider 路由、JD 解析、混合检索、匹配评分、Evidence Judge、Guard 规则、Gold Set | Prompt 包、评分实现、模型评估报告、Gold Set 指标 | Prompt/权重变更需 R0+R1 审批 |
| R4 | **浏览器扩展工程师** | 站点侧唯一执行端 | MV3 扩展：配对、采集、网络层解码/DOM 降级、四模块填充预览、风控暂停、8789 迁移 | 扩展包、选择器/proto 版本记录、契约测试、风控测试 | 无（改动强制 R8+R1 评审） |
| R5 | **前端工程师** | 控制台与编辑器 | React 控制台（采集/岗位池/候选/投递包/确认台/复盘看板/设置）、A4 编辑器、模板网格库 | Web 应用、组件、页面 E2E | 无 |
| R6 | **模板 / 渲染工程师**（可由 R2+R5 兼） | 模板正交模型与多格式导出 | Blueprint、DOCX 开源导入管线、Chromium/WeasyPrint/python-docx 渲染、回读校验、视觉回归 | 内置模板包、导入服务、渲染器、导出回归报告 | 模板入库许可需 R8 复核 |
| R7 | **QA / 测试工程师**（可兼任，但需独立视角） | 证明系统「对」且红线「做不到」 | 测试金字塔、契约测试、Gold Set/规则边界集/红队集、E2E、安全负例、验收取证 | 测试计划、自动化测试、验收证据包、缺陷登记 | 质量门禁一票否决 |
| R8 | **安全与隐私评审人**（兼职/轮值，必须独立） | loopback、聊天 PII、账号安全 | 信任边界审计、出站零外发断言、KEK/密钥检查、许可证扫描、红线代码评审 | 安全评审单、渗透/负例结果、license 报告 | 安全/隐私/风控事项一票否决 |
| R9 | **本机运维 / DevOps**（兼职） | 本地环境可装可恢复 | Compose、渲染镜像/字体、备份恢复、Runbook、发布顺序、版本兼容验证 | compose 配置、备份脚本、Runbook、发布记录 | 无 |

## 2. 职责边界（RACI 精简版）

R=负责执行，A=最终问责，C=被咨询，I=被知会。

| 事项 | R0 | R1 | R2 | R3 | R4 | R5 | R6 | R7 | R8 | R9 |
|---|---|---|---|---|---|---|---|---|---|---|
| 需求/筛选口径/候选决定 | A/R | C | — | C | — | — | — | I | — | — |
| 架构与 ADR | C | A/R | C | C | C | C | C | C | C | C |
| 契约（contracts/）变更 | I | A | R | R | R | R | R | C | C | — |
| 数据库迁移 | I | A | R | — | — | — | C | C | C | C |
| 扩展采集/解码/填充 | I | C | C | — | A/R | — | — | R | R | — |
| Prompt/评分权重 | A（审批） | A | — | R | — | — | — | R | C | — |
| 招呼语/简历内容 | A（最终确认每条实际外发内容） | C | — | R | C | — | C | R | — | — |
| 模板/DOCX 导入/渲染 | I | C | — | — | — | C | A/R | R | C（license） | C |
| 红线与外发审计 | I | C | C | C | C | C | C | R | A/R | C |
| 发布与备份恢复 | I | A | C | C | C | C | C | C | C | R |
| 阶段 Go/No-Go | A | R | C | C | C | C | C | R（质量） | R（安全） | C |

关键约束：
- **R0 与 R1 同为本人时**，产品取舍与架构取舍仍要分别记录（避免「因为好做所以改需求」不留痕）。
- **R8 不能由代码作者担任**；单人项目由本人在「安全评审单」上以独立时段（建议间隔 24 小时）复核，并用自动化断言兜底。
- AI 代理在任何行上只能是 R，不能是 A。

## 3. 两种人员配置方案

### 方案 A：单人全栈（最小配置，当前默认）

一人承担 R0–R9，外部协作只有 AI 编程代理。必须用流程补足评审缺失：

| 风险 | 补偿措施 |
|---|---|
| 作者自审 | 红线改动写「安全评审单」，隔夜复核；合并前跑全量负向测试 |
| 需求蔓延 | 每阶段只认 19 篇出口门禁；新需求进 backlog，不插当前阶段 |
| 测试盲区 | Gold Set / 规则边界集 / 红队集先于实现写；测试与实现分开任务做 |
| 账号风险 | 真实账号操作小批量、人工节奏；风控测试只用本地夹具，绝不自动化真实站点 |
| 知识单点 | 所有决策进 ADR/Runbook；关键操作有恢复演练记录 |

此配置下日历周期长（见 [03](03-排期与里程碑.md)），但合规性不降级。

### 方案 B：小队配置（2–4 人，推荐的效率配置）

| 人数 | 配置 | 分工建议 |
|---|---|---|
| 2 人 | 本人（R0+R1+R3 部分）+ 全栈工程师（R2+R5+R9） | 扩展（R4）与渲染（R6）由两人在 P1/P3 分别承担，QA/R8 互相评审 |
| 3 人 | 本人（R0+R1）+ 后端/AI（R2+R3）+ 前端/扩展（R4+R5+R6） | R7 由两人交叉兼任，R8 本人独立承担 |
| 4 人 | 3 人同上 + QA/安全（R7+R8） | R9 后端兼任；评审最完整，周期最短 |

## 4. 能力要求（招人/选 AI 任务时对照）

- **R2 后端**：Python 3.12、FastAPI、SQLAlchemy 2/Alembic、Redis 队列、WebSocket、pgvector；能写幂等并发测试。
- **R3 AI**：Prompt 工程与结构化输出、RAG/混合检索、评分可解释性、离线评估集设计；理解「相似≠证据」。
- **R4 扩展**：MV3 service worker、网络响应 hook 与 protobuf 解码、反爬风控常识（**用于规避风险而非绕过风控**）、幂等上报。
- **R5 前端**：React 18 + Vite + TS、TanStack Query、Zod、打印分页/A4 排版、画布/网格 UI。
- **R6 渲染**：OOXML/python-docx、无头 Chromium、WeasyPrint、中文字体与分页、DOCX 保真评估。
- **R7 QA**：契约测试（schemathesis）、Playwright、Gold Set 方法论、安全负例设计、指标取证。
- **R8 安全**：本地信任边界、静态加密、出站审计、许可证合规；不需要渗透攻防背景，但必须有数据隐私敏感度。
